01¿Qué hace la capa 5?

La capa de sesión gestiona el ciclo de vida de una conversación entre dos aplicaciones. Mientras la capa 4 se ocupa de que los datos lleguen correctamente, la capa 5 se ocupa de que la conversación tenga un principio, un desarrollo ordenado y un cierre controlado.

Apertura
Establecimiento
Negocia parámetros e identidades antes de intercambiar datos.
Continuidad
Mantenimiento
Mantiene el canal activo y gestiona tokens de acceso.
Recuperación
Sincronización
Inserta puntos de control para reanudar sin perder progreso.
Cierre
Terminación
Finaliza la sesión de forma ordenada y libera los recursos.
Idea clave
La capa 4 garantiza que los segmentos lleguen. La capa 5 garantiza que la conversación completa tenga contexto: quién habla, cuándo, con qué identidad y desde qué punto se puede continuar si se interrumpe.
Ejemplo cotidiano
Llamada telefónica
El "ring → hola → conversación → chau" es una sesión. Sin esta capa, cada frase llegaría sin saber a qué conversación pertenece.
Ejemplo de red
Sesión SSH
SSH establece una sesión autenticada sobre TCP. Todo el intercambio de comandos ocurre dentro de esa sesión, no como paquetes aislados.
Ejemplo de red
Sesión SMB
Cuando Windows accede a una carpeta compartida, negocia una sesión SMB: autenticación, permisos y contexto de la conexión antes de transferir archivos.
02Ubicación dentro del modelo OSI

Selecciona una capa para ver su función. La capa 5 se ubica entre el transporte (capa 4) y la presentación (capa 6), actuando como coordinadora de la conversación.

Capas adyacentes
Capa 4 (Transporte): entrega bytes confiablemente entre extremos. La capa 5 usa ese canal para construir una sesión con contexto.
Capa 6 (Presentación): cifra, comprime o transforma el formato de los datos. La sesión que administra la capa 5 es el contenedor de ese intercambio.
03Ciclo de vida de una sesión

Toda sesión recorre tres fases: establecimiento (negociación e identidad), intercambio de datos (la sesión está activa) y terminación (cierre ordenado y liberación de recursos).

04Control de diálogo

La capa 5 define quién habla y cuándo. Hay tres modos de comunicación según la dirección y simultaneidad del intercambio de datos.

Simplex
TV, radio, sensores
Un sensor IoT que solo envía temperatura hacia el servidor. El servidor no responde datos al sensor.
Half-duplex
Walkie-talkie, HTTP/1.0
HTTP/1.0: el cliente envía una petición, espera la respuesta completa y solo entonces envía otra. No hay intercambio simultáneo.
Full-duplex
Teléfono, WebSocket, SSH
En una sesión SSH ambas partes pueden enviar datos al mismo tiempo: el cliente escribe y el servidor responde sin esperar.
05Sincronización y puntos de control

En transferencias largas (archivos grandes, backups, sesiones FTP), la capa 5 puede insertar puntos de control. Si la conexión se interrumpe, la sesión se reanuda desde el último punto sin reiniciar desde el principio.

Nota sobre capas en la práctica
En el modelo TCP/IP real, la capa 5 no tiene una capa separada explícita. Sus funciones las implementan directamente los protocolos de aplicación (SSH, TLS, SMB, SIP). El modelo OSI sirve para analizar conceptualmente cada responsabilidad, no para mapear 1:1 con el software.

08SIP y gestión de sesiones VoIP

  

    
SIP (Session Initiation Protocol) es el protocolo de capa 5 más claro del modelo OSI: su única función es establecer, modificar y terminar sesiones multimedia (llamadas de voz, videoconferencias, mensajería). SIP no transporta audio ni video: eso lo hace RTP en capa 4.

Señalización · SIP
Gestiona la sesión
SIP usa mensajes de texto similares a HTTP: INVITE, ACK, BYE, CANCEL, OPTIONS. Puerto 5060 (UDP/TCP) y 5061 (TLS).

      
Datos · RTP
Transporta audio/video
Una vez que SIP establece la sesión, RTP (capa 4) transporta los streams de audio y video en tiempo real por puertos UDP negociados.

09Seguridad en la capa de sesión

  

    
Las sesiones son un objetivo frecuente de ataques porque representan identidad autenticada. Comprometer una sesión es equivalente a robar las credenciales del usuario durante su uso.

    

      
Ataque
Session Hijacking
El atacante roba el identificador de sesión (cookie, token) y lo usa para suplantar al usuario.

      
Ataque
Session Fixation
El atacante fuerza al usuario a usar un ID de sesión conocido previamente por él.

      
Ataque
Replay Attack
El atacante captura y reenvía mensajes de establecimiento de sesión para autenticarse.

Uso de HTTPS/TLS
Cifra los identificadores de sesión en tránsito. Sin TLS, las cookies viajan en texto plano.

      
Regenerar ID tras login
Previene session fixation: se emite un nuevo ID después de autenticar.

      
Timeout de sesión
Las sesiones inactivas expiran, limitando la ventana de uso de un token robado.

      
Flags HttpOnly y Secure
HttpOnly evita que JavaScript lea la cookie. Secure la envía solo por HTTPS.

      
Nonces y timestamps
Previenen replay attacks: cada mensaje lleva un valor único que no puede reutilizarse.

    

    

      
Relación con TLS

      
TLS implementa conceptos de capa 5 y 6 simultáneamente: gestión de sesión (session tickets, session ID, reanudación) en capa 5 y cifrado y formato en capa 6. Por eso a veces se dice que TLS "abarca" capas 5 y 6 del modelo OSI.

    

  







  
10Práctica: analizar sesiones con tcpdump y Wireshark

  

    
Esta práctica permite identificar el ciclo de vida de sesiones reales en capturas de red. Se analiza cómo distintos protocolos establecen, mantienen y cierran sesiones, y qué campos de la captura son relevantes en cada caso.


    
Paso 1Capturar sesiones SMB (compartición de archivos Windows)

    
terminal

    
sudo tcpdump -i eth0 -nn -s 0 -w smb_session.pcap tcp port 445

Filtros Wireshark:
smb2
smb2.cmd == 0           # Negotiate
smb2.cmd == 1           # Session Setup
smb2.sesid != 0         # sesiones activas

    
Qué observar
Busca la secuencia: TCP handshake → SMB2 Negotiate (cliente propone versiones) → Session Setup (autenticación NTLM o Kerberos) → Tree Connect (acceso al recurso compartido). Cada parte identifica el establecimiento de la sesión en capa 5.


    
Paso 2Capturar sesiones SSH

    
terminal

    
sudo tcpdump -i eth0 -nn -s 0 -w ssh_session.pcap tcp port 22
ssh usuario@servidor_en_la_red

Filtros Wireshark:
tcp.port == 22
ssh
tcp.flags.fin == 1      # cierre de sesión

    
Qué observar
El intercambio de banners (SSH-2.0-OpenSSH_x.x) es parte del establecimiento de sesión en capa 5. Luego verás Key Exchange (capa 6) y después tráfico cifrado. El cierre se observa con el flag FIN de TCP.


    
Paso 3Capturar sesiones SIP (VoIP)

    
terminal

    
sudo tcpdump -i eth0 -nn -s 0 -w sip_session.pcap "port 5060 or port 5061"

Filtros Wireshark:
sip
sip.Method == "INVITE"       # inicio de sesión (llamada)
sip.Method == "BYE"          # fin de sesión (colgar)
sip or rtp                   # sesión completa con audio


    
Paso 4Identificar reanudación de sesión TLS

    
terminal

    
sudo tcpdump -i eth0 -nn -s 0 -w tls_resumption.pcap tcp port 443
curl https://example.com   # primera conexión
curl https://example.com   # segunda conexión (puede reusar sesión)

Filtros Wireshark:
tls
tls.handshake.type == 1     # Client Hello
tls.handshake.type == 2     # Server Hello
tls.handshake.session_id    # buscar session ID reutilizado

    
Qué observar
Si la segunda conexión envía un Client Hello con el mismo Session ID o un Session Ticket, el servidor puede reanudar la sesión TLS sin hacer el handshake completo, ahorrando latencia. Este es un mecanismo de sesión en capa 5.


    
Paso 5Identificar NetBIOS Session Service

    
terminal

    
sudo tcpdump -i eth0 -nn -s 0 -w netbios.pcap "port 139 or port 137 or port 138"

Filtros Wireshark:
nbss              # NetBIOS Session Service (TCP 139)
nbns              # NetBIOS Name Service (UDP 137)
nbdgm             # NetBIOS Datagram Service (UDP 138)
