Capa 6 del modelo OSI
Codificación, compresión y cifrado

Presentación interactiva para comprender cómo la capa de presentación traduce, comprime y cifra los datos para que las aplicaciones puedan intercambiarlos sin importar el sistema operativo, el hardware o el idioma del texto.

Comenzar explicación Ir a práctica Wireshark
01¿Qué hace la capa 6?

La capa de presentación es el traductor universal de la red. Su trabajo es garantizar que los datos generados por una aplicación sean comprensibles para la aplicación del otro extremo, independientemente de diferencias de plataforma, lenguaje o formato.

Traducción
Codificación
Convierte texto entre juegos de caracteres: ASCII, UTF-8, UTF-16, EBCDIC. Garantiza que la "ñ" llegue correctamente.
Eficiencia
Compresión
Reduce el volumen de datos antes de enviarlos. gzip, deflate y Brotli son ejemplos activos en HTTP.
Privacidad
Cifrado
Transforma los datos en texto ilegible para terceros. TLS implementa el cifrado de capa 6 sobre la sesión de capa 5.
Formato
Serialización
Convierte estructuras de datos (objetos, listas) a un formato transmisible: JSON, XML, Protobuf, ASN.1.
Idea clave
La capa 5 controla cuándo y entre quiénes ocurre la conversación. La capa 6 controla en qué idioma y formato se expresa esa conversación, y si los contenidos están cifrados o comprimidos.
Ejemplo 1
Página web HTTPS
El servidor comprime el HTML con gzip (compresión L6), lo cifra con TLS (cifrado L6) y el navegador invierte el proceso al recibirlo.
Ejemplo 2
Texto multilingüe
El servidor envía "hola → مرحبا → 你好" en UTF-8. La capa 6 asegura que cada extremo interprete los mismos bytes como los mismos caracteres.
Ejemplo 3
API REST
La aplicación serializa un objeto Python o Java a JSON (texto UTF-8). La otra aplicación deserializa ese JSON a su propio objeto nativo.
02Ubicación dentro del modelo OSI

Selecciona una capa para ver su función. La capa 6 se ubica entre la sesión (capa 5) y la aplicación (capa 7), preparando los datos para su uso final.

Por qué la capa 6 existe
Sin una capa de presentación, cada aplicación debería encargarse de convertir formatos, comprimir y cifrar por sí sola. La capa 6 centraliza esas responsabilidades. En la práctica, los protocolos modernos (TLS, HTTP/2) absorben estas funciones, por eso OSI y TCP/IP no se mapean 1:1.
03Codificación de caracteres

Un carácter es solo un concepto. Para transmitirlo por la red hay que convertirlo a bytes. Escribe texto en el campo y observa cómo cada codificación lo representa de forma distinta.

Referencia de codificaciones
ASCII (7 bits, 128 caracteres): solo inglés. Los caracteres 0–127 son iguales en ASCII y UTF-8. UTF-8: codificación variable (1–4 bytes). Compatible con ASCII. Es el estándar de Internet. UTF-16: 2 o 4 bytes por carácter. Usado en Windows internamente y en Java. EBCDIC: IBM mainframes. Completamente diferente de ASCII.
ASCII
128 caracteres · 1 byte · solo inglés · código 0x00–0x7F
Latin-1 / ISO 8859-1
256 caracteres · 1 byte · extiende ASCII con acentos europeos
UTF-8
1–4 bytes · compatible con ASCII · estándar de la web y de Linux
UTF-16
2 o 4 bytes · BOM indica endianness · usado en Windows y Java
UTF-32
4 bytes fijos · simple pero ineficiente · usado en procesamiento interno
04Compresión de datos

La compresión reduce el tamaño de los datos antes de enviarlos, ahorrando ancho de banda y tiempo de transferencia. Selecciona un tipo de contenido para ver cómo distintos algoritmos lo comprimirían.

Tipos de compresión
Sin pérdida (lossless): recupera los datos exactos. Ideal para texto, código, certificados. Algoritmos: gzip, zlib, Brotli, LZ4, Zstandard. Con pérdida (lossy): descarta información irrelevante para el ojo/oído humano. Ideal para multimedia. Algoritmos: JPEG, MP3, H.264, Opus. En HTTP: el cliente declara qué acepta con Accept-Encoding: gzip, br; el servidor responde con Content-Encoding: gzip.
gzip / deflate
Lossless · LZ77 + Huffman · estándar en HTTP/1.1 y HTTP/2 · típico: 70–80% reducción en HTML/CSS
Brotli
Lossless · Google · mejor ratio que gzip en texto · usado en HTTP/2 y HTTP/3 modernos
LZ4 / Zstandard
Lossless · muy rápidos · usados en bases de datos, contenedores Docker, almacenamiento
JPEG / WebP
Lossy · para imágenes · elimina detalles imperceptibles al ojo · 80-95% reducción
H.264 / H.265 / AV1
Lossy · para video · compresión temporal entre frames · estándar en streaming
05Cifrado: simétrico y asimétrico

La capa 6 es responsable del cifrado de los datos antes de transmitirlos. Existen dos grandes familias de algoritmos: simétrico (misma clave para cifrar y descifrar) y asimétrico (clave pública cifra, clave privada descifra).

Descripción
Simétrico (AES, ChaCha20)
Misma clave en ambos lados · muy rápido · problema: ¿cómo compartir la clave de forma segura?
Asimétrico (RSA, ECDH)
Clave pública libre + clave privada secreta · lento · resuelve el intercambio de claves
Híbrido (TLS 1.3)
Asimétrico para intercambiar la clave · simétrico para cifrar los datos · lo mejor de ambos
Hash (SHA-256, SHA-3)
No es cifrado: es resumen unidireccional · verifica integridad sin revelar el contenido
06TLS — Capa 6 y capa 5 en acción simultánea

TLS (Transport Layer Security) es el protocolo que más claramente combina funciones de capa 5 (gestión de sesión) y capa 6 (cifrado y formato). Cada mensaje TLS se denomina registro TLS y tiene una estructura precisa.

Detalle
Capa 5 en TLS
Sesión y reanudación
Session ID, Session Ticket y 0-RTT permiten reanudar sesiones TLS sin repetir el handshake completo.
Capa 6 en TLS
Cifrado y formato
TLS cifra cada registro con AES-GCM o ChaCha20-Poly1305 y añade un MAC de autenticación.
Certificados X.509
Identidad verificada
Los certificados están codificados en ASN.1/DER (capa 6) y contienen clave pública, identidad y firma de la CA.
Filtros Wireshark para TLS y certificados
tls                          # todo el tráfico TLS
tls.handshake.type == 1      # Client Hello (inicio de sesión)
tls.handshake.type == 11     # Certificate (certificado del servidor)
tls.handshake.type == 20     # Finished (fin del handshake)
tls.record.content_type == 23  # Application Data (datos cifrados)
x509sat.CountryName          # datos del certificado X.509

08Tipos MIME y formatos multimedia

  

    
MIME (Multipurpose Internet Mail Extensions) es el sistema que identifica el tipo de contenido de un recurso. La capa 6 usa esta información para saber cómo interpretar los bytes: ¿son texto, imagen, audio, video o datos binarios?

    

      
      
      
      
      
      
    

    

      
CategoríaTipo MIMEDescripción

      

    

    

      
MIME en HTTP

      
En una respuesta HTTP, el servidor indica el tipo de contenido con la cabecera Content-Type: text/html; charset=UTF-8. El cliente (navegador) usa esa información para renderizar correctamente el contenido, sin depender de la extensión del archivo.

    

    

      
MIME en HTTP / Wireshark

      
http.content_type             # filtrar por tipo MIME en Wireshark
http.content_type == "application/json"
http.content_encoding         # ver si está comprimido (gzip, br)
http.content_length           # tamaño en bytes del contenido

    

  







  
09Endianness y representación binaria

  

    
El endianness define el orden en que los bytes de un número multi-byte se almacenan en memoria y se transmiten por la red. Es una función de capa 6: asegura que ambos extremos interpreten los mismos bytes como el mismo número.

    

      Número (decimal o 0x hex):
      
      
    

    

    

    

      
Regla de la red

      
Network byte order = Big-endian. Los protocolos de red (IP, TCP, UDP) envían siempre el byte más significativo primero. Los procesadores Intel/AMD usan little-endian internamente. La capa de presentación (o el código de red) realiza la conversión con funciones como htons() (host to network short) y ntohl() (network to host long).

    

    

      
Big-endian (red)
Byte más significativo primero · IP, TCP, UDP, HTTP/2 frames · arquitecturas SPARC, MIPS

      
Little-endian (PC)
Byte menos significativo primero · Intel x86/x64, AMD64, ARM (por defecto) · Windows, Linux en PC

      
htons() / htonl()
Host To Network Short/Long · convierte de little-endian de la CPU a big-endian de la red

      
ntohs() / ntohl()
Network To Host Short/Long · convierte de big-endian de la red a little-endian de la CPU

    

  







  
10Práctica: analizar codificación, compresión y cifrado con Wireshark

  

    
Esta práctica permite observar las funciones de la capa 6 en capturas reales: tipo de contenido MIME, cabeceras de codificación/compresión, registros TLS y estructura de certificados X.509.


    
Paso 1Capturar HTTP con compresión gzip/Brotli

    
terminal

    
sudo tcpdump -i eth0 -nn -s 0 -w http_compress.pcap tcp port 80
curl -H "Accept-Encoding: gzip, deflate, br" http://example.com

# Filtros Wireshark:
http.content_encoding        # ver compresión usada
http.content_type            # tipo MIME del contenido
http.response.code == 200    # respuestas exitosas

    
Qué observar
En la cabecera de respuesta HTTP busca Content-Encoding: gzip (o br para Brotli). El tamaño del cuerpo comprimido comparado con el Content-Length original muestra la efectividad de la compresión de capa 6.


    
Paso 2Inspeccionar certificados TLS (X.509)

    
terminal

    
sudo tcpdump -i eth0 -nn -s 0 -w tls_cert.pcap tcp port 443
curl https://utu.edu.uy

# Filtros Wireshark:
tls.handshake.type == 11     # paquete con Certificate
x509sat.CountryName          # país del certificado
x509sat.CommonName           # nombre del dominio
tls.handshake.extensions_server_name  # SNI: nombre solicitado


    
Paso 3Ver codificación de texto en HTTP

    
terminal

    
sudo tcpdump -i lo -nn -s 0 -w http_utf8.pcap tcp port 8080
python3 -c "
import http.server, socketserver
class H(http.server.BaseHTTPRequestHandler):
  def do_GET(self):
    body = 'Hola ñ á é € 你好 مرحبا'.encode('utf-8')
    self.send_response(200)
    self.send_header('Content-Type','text/plain; charset=UTF-8')
    self.end_headers(); self.wfile.write(body)
with socketserver.TCPServer(('',8080),H) as s: s.serve_forever()
"
curl http://127.0.0.1:8080

# Filtros Wireshark:
http
tcp.port == 8080
data-text-lines                # ver datos de texto en Wireshark

    
Qué observar
Busca la cabecera Content-Type: text/plain; charset=UTF-8. Luego en el panel hexadecimal observa que los caracteres ASCII (H, o, l, a) usan 1 byte, mientras que la ñ usa 2 bytes (0xC3 0xB1), la € usa 3 bytes (0xE2 0x82 0xAC) y los caracteres CJK usan 3 bytes. Esta es la codificación UTF-8 en acción.
