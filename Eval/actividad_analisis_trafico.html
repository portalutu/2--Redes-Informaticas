Actividad guiada de 20 pasos para identificar dispositivos, protocolos y comportamientos en una captura de red real usando el Simulador Wireshark. Al finalizar la práctica se generará un ejemplo de informe profesional de analisis.

Antes de empezar — abrir el simulador

Abre en otra pestaña o ventana el archivo wireshark_simulador.html y carga la captura 500_practica_red_192_168_1.txt (o .txt). Usa ese simulador para responder las preguntas de cada paso. Al finalizar: Utiliza el botón para exportar como PPDF y carga el archivo generado en la carpeta designada para la entrega.

01
Cargar la captura en el simulador
Objetivo · Familiarizarse con la interfaz y registrar datos generales de la captura
▼

El primer paso en cualquier análisis es entender el alcance de la captura: cuántos paquetes contiene, cuánto tiempo duró y qué interfaz se usó. Esta información establece el contexto de todo el análisis posterior.

🔍 Tarea

Arrastra el archivo practica_red_192_168_1.pcap (o el .txt) sobre la zona de carga del simulador. Observa la barra de título de la captura y el panel de estadísticas.

El número de paquetes aparece en la barra superior del simulador tras la carga. El tiempo del último paquete es el valor Tiempo de la última fila de la tabla. Las estadísticas están en la tarjeta 03 al pie.

02
Identificar la red
Objetivo · Determinar dirección de red, máscara y broadcast
▼

Antes de analizar el tráfico es fundamental saber en qué red se produjo la captura. La dirección de red, máscara y broadcast delimitan el espacio de direcciones válidas y permiten identificar qué tráfico es local y cuál sale hacia Internet.

🔍 Tarea

Observa las IPs que aparecen como Origen y Destino. Busca patrones en los primeros octetos. Filtra por ARP para ver IPs locales. Filtra por DHCP para ver la máscara ofrecida.

Filtro: arp Filtro: dhcp

Las IPs locales empiezan con los mismos primeros tres octetos. En un paquete DHCP Offer, la capa de aplicación muestra la opción Subnet mask que el servidor envía al cliente.

03
Inventario de dispositivos
Objetivo · Listar todos los equipos que participan en la captura
▼

Un analista de red siempre comienza por entender quiénes están en la red. Cada dispositivo tiene una IP única y una MAC única. Listar estos pares es el primer paso del inventario.

🔍 Tarea

Revisa las columnas Origen y Destino en toda la captura. Anota cada IP/MAC única que aparezca. Filtra por ARP para obtener la tabla MAC↔IP más fácilmente.

Filtro: arp
IPMAC addressRol / nombre

Con el filtro arp cada fila muestra un par IP/MAC en los campos Origen y Destino. Las respuestas ARP ("is at") son las más directas porque muestran MAC e IP del respondedor.

04
Distinguir sistemas operativos
Objetivo · Identificar hosts Windows y Linux por sus protocolos y MACs
▼

Los sistemas operativos dejan "huellas" en la red: Windows usa NetBIOS y SMB; Linux usa mDNS y NFS. Las MACs también revelan el fabricante del adaptador de red.

🔍 Tarea

Filtra por nbns (solo Windows) y por mdns (Linux/macOS). Observa qué IPs generan cada tipo. Luego filtra por smb2 y nfs.

Filtro: nbns Filtro: mdns Filtro: smb2 Filtro: nfs

Los prefijos de MAC identifican fabricantes: 00:50:56 = VMware (usado por VMs Windows), 08:00:27 = VirtualBox, 00:0c:29 = VMware (Linux), 52:54:00 = QEMU/KVM (Linux).

05
Infraestructura de red
Objetivo · Identificar gateway, servidor DNS y NAS
▼

Toda red tiene infraestructura compartida: un gateway (puerta de enlace) que enruta hacia Internet, un servidor DNS que resuelve nombres, y posiblemente servidores de archivos como un NAS.

🔍 Tarea

En un paquete DHCP Offer, el árbol de disección muestra las opciones que el servidor envía: Router (gateway) y DNS. Para el NAS busca quién recibe tráfico SMB2 y NFS.

Filtro: dhcp Filtro: smb2

En un paquete DHCP Offer, haz clic sobre él y expande el árbol de disección → Dynamic Host Configuration Protocol (Offer). Las opciones 3 (Router) y 6 (DNS) están listadas ahí.

06
Protocolo ARP — Resolución de direcciones
Objetivo · Analizar el proceso de resolución MAC desde una IP
▼

ARP (Address Resolution Protocol) traduce IPs a MACs en la red local. Sin ARP, un equipo no puede enviar tramas Ethernet aunque conozca la IP de destino. Cada conversación comienza con ARP.

🔍 Tarea

Filtra por ARP. Busca un par Request/Reply consecutivo (dos filas seguidas donde la primera dice "Who has…" y la segunda "is at…"). Haz clic en cada uno y analiza el árbol de disección.

Filtro: arp

El Request se envía a ff:ff:ff:ff:ff:ff (broadcast) porque no se conoce la MAC destino. El Reply es unicast: solo el dueño de esa IP responde. El campo Opcode en el árbol distingue Request (1) de Reply (2).

07
DHCP — Proceso DORA completo
Objetivo · Documentar los cuatro mensajes del proceso de asignación de IP
▼

DHCP asigna IPs automáticamente mediante cuatro mensajes: Discover → Offer → Request → ACK. Cada uno tiene un rol específico en la negociación.

🔍 Tarea

Filtra por DHCP. Elige un Transaction ID (aparece en la columna Info) y sigue los cuatro mensajes que comparten ese ID. Haz clic en el Offer y expande el árbol.

Filtro: dhcp

El Transaction ID es el mismo en los cuatro mensajes de un mismo ciclo DORA. El cliente aún no tiene IP al enviar el Discover, por eso usa 0.0.0.0 como origen y 255.255.255.255 como destino (broadcast).

08
DNS — Consulta y respuesta exitosa
Objetivo · Analizar una resolución de nombre completa (query + response)
▼

DNS traduce nombres de dominio a IPs. Cada consulta tiene una respuesta que incluye la IP buscada y el TTL (tiempo en segundos que puede guardarse en caché). DNS usa UDP puerto 53 para mayor velocidad.

🔍 Tarea

Filtra por DNS. Elige una consulta (Standard query) y su respuesta (Standard query response) que compartan el mismo Transaction ID. Analiza el árbol de disección de ambos.

Filtro: dns

La consulta siempre va al puerto 53. El puerto origen es efímero (aleatorio >49151). La respuesta tiene el mismo Transaction ID que la consulta. En el árbol puedes ver Name consultado y Address (la IP respondida).

09
DNS fallido — NXDOMAIN
Objetivo · Identificar y explicar una resolución DNS que falla
▼

No todas las consultas DNS son exitosas. Cuando un nombre no existe, el servidor responde con NXDOMAIN (Non-Existent Domain, código de error 3). Esto puede indicar typos, dominios vencidos o configuraciones incorrectas.

🔍 Tarea

Filtra por DNS y busca en la columna Info el texto "No such name". Haz clic en ese paquete y analiza su árbol de disección.

Filtro: dns
Buscar en Info: no such name

El campo Flags en el árbol DNS de la respuesta muestra rcode: 3 cuando el dominio no existe. El árbol también muestra que Answer RRs: 0 (ninguna respuesta válida).

10
TCP — Three-way handshake
Objetivo · Identificar y documentar el establecimiento de una conexión TCP
▼

TCP establece conexiones mediante tres pasos: SYN → SYN,ACK → ACK. Este handshake garantiza que ambos lados están listos y acuerdan los números de secuencia iniciales antes de transmitir datos.

🔍 Tarea

Filtra por TCP. Busca tres paquetes consecutivos entre el mismo par de IPs donde los flags sean [SYN], [SYN, ACK], [ACK]. Analiza el árbol de disección del primer SYN.

Filtro: tcp

En el árbol TCP del SYN, el campo Flags muestra 0x002 (SYN). El Sequence number del SYN es el ISN del cliente. En el SYN-ACK el servidor elige su propio ISN y confirma el ISN del cliente con Acknowledgment number = ISN_cliente + 1.

11
HTTP — Tráfico web sin cifrar
Objetivo · Leer una solicitud HTTP y su respuesta; evaluar la privacidad
▼

HTTP (puerto 80) transmite todo en texto plano. Cualquiera que capture la red puede leer las solicitudes y respuestas completas, incluyendo credenciales o contenido sensible. HTTPS cifra esto con TLS.

🔍 Tarea

Filtra por HTTP. Busca un par GET + respuesta (200 OK o 404). Haz clic en el GET y analiza la columna Info y el árbol.

Filtro: http

La columna Info del paquete HTTP GET muestra directamente la primera línea de la solicitud. El User-Agent identifica el sistema operativo y navegador del cliente — es útil para detectar qué equipos son Windows y cuáles Linux.

12
SMB2 — Windows accede al NAS
Objetivo · Identificar el protocolo de compartición de archivos de Windows
▼

SMB2 (Server Message Block v2) es el protocolo de Windows para compartir archivos, impresoras y recursos en red. Opera sobre TCP puerto 445. El NAS sirve como almacenamiento centralizado.

🔍 Tarea

Filtra por SMB2. Analiza los paquetes: qué IPs son los clientes, cuál es el servidor, y qué comandos SMB2 aparecen (Negotiate, Session Setup, etc.).

Filtro: smb2

SMB2 siempre va a la IP .10 (el NAS) en esta captura. El primer intercambio es siempre Negotiate (el cliente propone versiones SMB) seguido de Session Setup (autenticación).

13
NFS — Linux accede al NAS
Objetivo · Identificar el sistema de archivos en red de Linux
▼

NFS (Network File System) es el equivalente Linux/Unix de SMB. Usa UDP puerto 2049 y el protocolo RPC (Remote Procedure Call) para montar sistemas de archivos remotos.

🔍 Tarea

Filtra por NFS. Compara con el tráfico SMB del paso anterior: ¿qué diferencias ves en protocolos de transporte (TCP vs UDP), puertos y sistemas operativos clientes?

Filtro: nfs

NFS usa UDP 2049 por defecto. La operación NULL en RPC es el equivalente a un "ping" de verificación: el cliente comprueba que el servidor NFS responde antes de montar el filesystem.

14
SSH — Conexiones seguras
Objetivo · Identificar sesiones SSH y entender el intercambio de banners
▼

SSH (Secure Shell, puerto 22) cifra toda la comunicación. Sin embargo, el intercambio inicial de banners (versiones) ocurre en texto plano antes de que el cifrado se active, revelando versiones del software.

🔍 Tarea

Filtra por SSH. Busca paquetes donde la Info muestre un banner ("Servidor: SSH-2.0-…" o "Cliente: SSH-2.0-…"). Analiza el árbol de disección.

Filtro: ssh

Los banners SSH son el primer intercambio antes del Key Exchange. Revelan nombre del sistema operativo (Ubuntu, Debian) y versión exacta de OpenSSH. Los administradores de seguridad suelen ocultar o modificar estos banners.

15
ICMP — Ping y diagnóstico de red
Objetivo · Analizar mensajes Echo Request/Reply y entender el TTL
▼

ICMP (Internet Control Message Protocol) es la herramienta básica de diagnóstico de red. El comando ping envía Echo Request (tipo 8) y espera Echo Reply (tipo 0). El TTL (Time To Live) indica cuántos saltos puede viajar el paquete.

🔍 Tarea

Filtra por ICMP. Elige un par Echo Request / Echo Reply. Compara el árbol de disección de ambos, especialmente el TTL y los campos ID y Seq.

Filtro: icmp

El TTL suele ser 64 en Linux y 128 en Windows al salir. Cada router que reenvía el paquete resta 1. Si llega a 0, el router descarta el paquete y envía un ICMP Time Exceeded. El ID del Request debe coincidir con el del Reply.

16
NetBIOS — Resolución de nombres Windows
Objetivo · Entender cómo Windows descubre equipos sin servidor DNS
▼

NetBIOS Name Service (puerto UDP 137) permite a Windows descubrir equipos en la red local mediante broadcast, sin necesitar un servidor DNS. Es un protocolo antiguo pero aún presente en redes Windows.

🔍 Tarea

Filtra por NBNS. Observa qué IPs generan estos paquetes, hacia dónde van (¿broadcast?) y qué dice la columna Info.

Filtro: nbns

NBNS se envía siempre a la dirección de broadcast de la subred (.255). Esto significa que todos los equipos de la red reciben estas consultas, lo que puede revelar nombres de equipos a un atacante que esté escuchando.

17
mDNS — Resolución local en Linux
Objetivo · Entender el descubrimiento de servicios multicast en redes locales
▼

mDNS (Multicast DNS, puerto UDP 5353) permite que Linux y macOS resuelvan nombres .local sin servidor DNS. Usa la dirección multicast 224.0.0.251 en lugar de broadcast, lo que es más eficiente.

🔍 Tarea

Filtra por MDNS. Observa las IPs de origen, el destino multicast y los nombres .local consultados en la columna Info.

Filtro: mdns

224.0.0.251 es la dirección multicast reservada para mDNS (RFC 6762). Solo los equipos que "escuchan" ese grupo reciben los paquetes, a diferencia del broadcast que llega a todos aunque no estén interesados.

18
Árbol de disección — Análisis por capas OSI
Objetivo · Usar el panel de disección para descomponer un paquete en sus capas
▼

El árbol de disección (panel medio en Wireshark) muestra cada paquete descompuesto capa por capa, desde la trama Ethernet hasta la aplicación. Es la herramienta principal para entender qué contiene un paquete.

🔍 Tarea

Elige un paquete DNS cualquiera. Haz clic sobre él y expande todos los nodos del árbol de disección (Frame, Ethernet, IPv4, UDP, DNS). Anota cada campo importante.

Filtro: dns

Haz clic en el triángulo ▶ de cada nodo para expandirlo. El nodo Frame corresponde a la capa física/enlace (tamaño total). Ethernet II = capa 2. IPv4 = capa 3. UDP = capa 4. DNS = capa de aplicación (capa 7).

19
Vista hexadecimal — Leer bytes crudos
Objetivo · Interpretar el panel hex dump y relacionarlo con los campos del protocolo
▼

El hex dump muestra los bytes reales del paquete en hexadecimal y ASCII. Los primeros 6 bytes son la MAC destino, los siguientes 6 la MAC origen, y los siguientes 2 el EtherType. Esta vista muestra exactamente lo que viaja por el cable.

🔍 Tarea

Esta actividad requiere el archivo .pcap (no el .txt). Carga el PCAP, selecciona un paquete ARP y analiza el hex dump. Los primeros 14 bytes son la cabecera Ethernet.

Requiere: archivo .pcap

Offset 0000: bytes 0–15. Los 6 primeros son MAC dst. Bytes 6–11 son MAC src. Bytes 12–13 son EtherType: 08 06 = ARP, 08 00 = IPv4. A partir del byte 14 empieza la carga útil (payload) del protocolo.
